# Zenn記事の書き方

このファイルは、このリポジトリで記事を書くときの表現と構成の基準です。
用字用語として機械的に判定できるものはtextlintへ置き、文脈を読まないと判断できないものはこのファイルへ残します。

## 参考にする記事

新しい記事を書くときは、同じ題材を扱った既存記事を最初に確認します。
文体については、AIによる執筆支援を前提としていない次の記事を主な参考にします。

- `articles/introduction_of_mise.md`
- `articles/connect-cloud9-via-remote-ssh.md`
- `articles/cdktf-for-usual-terraform-users.md`

題材に近い記事がほかにある場合は、その記事で説明済みの内容と用語も確認します。
以前の記事を要約し直すのではなく、読者が次に知りたくなることから書き始めます。

## 筆者の経験を補わない

筆者が過去に使ったツールや運用方法は、既存記事または本人の説明で確認できたものだけを書きます。
「一般的には使うはず」「比較に必要だから使ったことにする」といった補完はしません。

実際に使ったものと、記事を書くために今回初めて試したものも分けます。

```md
自分はPython製CLIをグローバルのpipでインストールしていました。

今回、miseのpipx backendが内部で何を実行するのかを確認するため、HTTPieを使って試しました。
```

## 説明の順番

複数の例や選択肢を出す前に、何を確認するための例なのかを書きます。
説明していない選択肢を前提に、「これは採用する」「これは採用しない」と並べません。

次の順番を基本にします。

1. 既存記事で説明済みの内容
2. 今回確認したい疑問
3. 例を選んだ理由
4. 設定またはコマンド
5. 実際の出力
6. 出力から分かったこと

機能一覧を載せる場合も、一覧そのものを記事の結論にはしません。
記事で詳しく見るものと、その理由を一覧の前に書きます。

## 公式情報と実機確認を分ける

仕様やデフォルト値を説明するときは、公式ドキュメントまたは公式リポジトリへのリンクを近くに置きます。
バージョンによって挙動が変わるものは、可能ならタグやコミットへ固定したリンクも付けます。
`experimental`である機能は、記事を書き終えた時点か、公開直前の最新版で状態を確認します。

公式ドキュメントの表現そのものが判断の根拠になる場合は、必要な範囲だけ引用します。
リンクを付けるだけで十分な場合は、引用を増やしません。

手元で確認した結果には、次の情報を先に書きます。

- 実行日
- OSとアーキテクチャ
- 対象ツールのバージョン
- 普段の設定と分けた場合は、その理由

ドキュメントで確認した仕様と、手元で観測した結果を同じ文で断定しないようにします。

## コマンドと出力

コマンド、出力、説明は別々にします。
すべてを1つの文章へ詰め込みません。

```shell
mise lock --platform macos-arm64
```

```toml
[[tools.node]]
version = "24.19.0"
backend = "core:node"
```

この結果から何が分かるのかを、コードブロックのあとに書きます。

bash、zsh、fishで同じように実行できるコマンドは、コードフェンスを`shell`にします。
シェル固有の構文を使う場合は、実際のシェル名を指定します。
同じコマンドをシェルごとに繰り返さず、書き方が異なる場合にだけ必要な例を併記します。

実機確認に使ったシェルは、コードフェンスではなく検証条件として本文に書きます。

出力が短い場合は省略せずに載せます。
長い出力から一部を見せる場合は、`jq`や`rg`などで同じ部分を取り出せるコマンドも書きます。
手作業で途中を削り、実際の出力に見える形で`...`を加えません。

プラットフォーム固有のURLやファイル名を出す前に、自分の環境を説明します。
例に使うツールが一般的でない場合は、何をするツールなのかと、なぜその検証に使うのかを書きます。

## 日本語の組み立て

1つの文へ条件を重ねすぎないようにします。
デフォルトの動作、条件を満たす場合、満たさない場合を別の文または箇条書きへ分けます。

公式の機能名、設定名、コマンドは原文の表記を残します。
製品固有の概念も、一般名詞と区別する必要がある場合は英語で表記します。
たとえば、miseが実行単位として扱うものは`task`、公式の機能名はFile Tasksと表記します。

技術用語としてカタカナ表記が定着しているものは、無理に日本語へ置き換えません。
`editor`や`interpreter`のような一般的な技術用語は、エディタやインタプリタと表記します。
英語、日本語、カタカナのどれを使うかは、文脈と読みやすさから判断します。
`help`や`shell completion`のように英語表記を残す場合は、文中で区別できるようにインラインコードとして表記します。

主語や対象があいまいな抽象表現より、誰が何をするのかを書きます。

```md
# 分かりづらい
tasksをチーム共通の確認入口にしています。

# 書き換え例
開発環境がそろっているか、チーム全員が同じtaskで確認できるようにしています。
```

同じ書き出しや接続詞が続く場合は見直します。
ただし、「一方で」「そのため」などの語を一律に禁止するものではありません。
前後の関係を説明するために必要かどうかで判断します。

`〜は、〜です`のように、主題の直後へ機械的に読点を置かないようにします。
読点は、文の意味を区切る必要がある場所に使います。

記事の本文は、原則として一文ごとに改行します。
一文が長い場合は読みやすい位置で途中改行できます。
短い文が続く場合は、段落を不自然に細かく分けないよう調整します。

脚注は`説明[^1]。`のように句点の直前へ置きます。
句点の後ろへ置くと、`@cffnpwr/textlint-rule-sentence-per-line`が脚注記号を別の文として扱います。

## 指摘を受けた表現

次の表は、レビューで分かりづらいと指摘された表現と、書き換えるときの考え方をまとめたものです。
右側をそのまま貼るのではなく、記事の対象に合わせて具体化します。

| 避けたい表現 | 書き換え方 |
| --- | --- |
| `〜の候補にしています` | 実際にしていることを書く。例: `〜を[tools]で管理しています` |
| `チーム共通の確認入口` | 誰が何を確認するのかを書く |
| `〜へ寄せる範囲` | `miseで管理するもの、パッケージマネージャーで管理するもの`のように対象を並べる |
| `〜へ移すつもりはありません` | 現在の管理場所と、そこへ置く理由を書く |
| `新しいregistry entry` | `registryへtoolを新しく登録するとき` |
| `普段のmise環境と保存先を分ける` | 既存の設定やキャッシュの影響を避けるため、何の保存先を分けたのかを書く |
| `Python applicationが使うlibrary` | `Pythonアプリケーションから読み込むライブラリ` |
| `ほかのpackageと一緒に更新したいCLI` | Prettier本体とプラグインなど、同じ`lockfile`で管理する具体例を書く |
| `判断に必要な行だけ残します` | 何を省き、どのコマンドと結果を載せるのかを書く |

本人が手作業で直した表現は、明確な理由がない限り以前の表現へ戻しません。
新しい指摘でほかの記事にも使えるものが出た場合は、この表へ追加します。

## textlintへ追加する基準

textlintへ追加するのは、文脈にかかわらず同じ置換ができる表記だけです。
置換によって主語、対象、意味が変わる表現は追加しません。

一行に複数の文が書かれていないかは、`@cffnpwr/textlint-rule-sentence-per-line`で検出します。
このルールは一文の途中での改行を許容します。
長い文をどこで改行するかや、不自然に短い行になっていないかは判断しないため、レビュー時に確認します。

次のものは文章全体を読まないと判断できないため、このガイドとレビューで確認します。

- 主語が不足している文章
- 例を出す順番
- 見出しと本文の関係
- 条件分岐が多い文章
- 抽象的な比喩
- 接続詞の使いすぎ

リポジトリ固有のprhルールは、複数の記事で繰り返し現れる表記を対象にします。
文脈にかかわらず、同じ置換ができる場合に追加します。
特定の記事で一度だけ指摘された表現や、前後の文脈によって書き換え方が変わる表現はprhへ追加せず、このガイドとレビューで扱います。
